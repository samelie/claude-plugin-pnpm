# /team-kit-run — Execute work as a native-workflow multi-agent run

## When to use

Three entry modes:
1. **Approved `team-plan.md`** (from `team-kit-create`) — **author (native) → lint → save → run** the committed spine `plan.workflow.js`. See `## Entry-mode-1 — committed spine (native author → lint → save)` below.
2. **Direct task** via the canonical invocation contract below — clear task that doesn't need the full clarify/explore planning ceremony. (Most common.)
3. **Saved template workflow** (`/monorepo-health`, etc.) — fully canned, parameterized via `args`.

NOT for: tiny 1–3 file tight-coupling fixes (single agent, no orchestration); anything still needing requirements clarification (run `team-kit-create` first).

### Workflow cost model — model tiering, not cache sharing

Workflow `agent()` calls are **named subagents with isolated caches** — live probe `wf_16f795f9-f2d` showed followers re-create ~14.5k tokens each (even warm + serial); there is NO cross-agent prefix reuse. A workflow fanning out N agents that all need the same big blob pays N× for it. Two consequences:

- **Keep workflow prompts lean** — push shared bulk to disk (`team-session/`); each agent reads only its slice.
- **Model tiering IS the cost lever** — `opts.model:'sonnet'` on mechanical/review/finalize stages, `'haiku'` for O(1) gate mechanics (preflight assertions, disk audits); reserve the inherited session model (currently fable) for implement/design (rule 13). There is no cache-sharing lever on the workflow path.

### Rule 15 addendum — the "dark agent" is a maxTurns KILL, not platform flakiness (forensics 2026-07-23, mono-cal tenancy: 19 dark agents across 3 runs, transcript-verified)

An agent that returns EMPTY with zero artifact is almost certainly a **frontmatter `maxTurns` cap kill**, and it is DETERMINISTIC, not intermittent. Mechanism (proven by transcript tails of all 19 dark agents): the cap fires mid tool-loop — terminal record is a `user` tool_result after an assistant `stop_reason:"tool_use"`, NO closing assistant turn, zero `end_turn`, zero errors. The workflow captures the TERMINAL record's text as the result → `""`, with no reason field anywhere. Because agents write their report + STATUS LAST by convention, a cap kill also destroys the artifact `auditEmpty` looks for — empty+no-artifact is the cap-kill signature, NOT proof of no work (dead coders' source EDITS survive; check git diff).

Predictor (perfect partition of the 2026-07-23 roster): **capped `maxTurns` AND O(changed-files) workload.** Dark: reviewer (cap 15 — roster minimum — reads the whole diff; died 6/6), tester (cap 25, touches most files; died 6/6 across runs 1+3), coder (cap 30; only the 5 broadest tasks died, 10 smaller finished at 7–25 turns). Never dark: spec-reviewer + goal-auditor (NO cap — one spec-reviewer finished at 30 turns), verifier (cap 30 but O(1) fixed-gate work, peaks ~12). Model/effort/preloaded-skills do NOT predict it.

Mitigations: (a) RESOLVED 2026-07-23 — `maxTurns` REMOVED from all 8 capped team agents (runaway protection belongs to the orchestration layer: workflow budget guard, agent-count cap, `/workflows` kill switch, natural context ceiling — a turn cap kills silently and destroys the report evidence). If a cap ever reappears in `.claude/agents/<type>.md` frontmatter, treat it as the prime dark-agent suspect; (b) on empty+no-artifact, read `<transcriptDir>/journal.jsonl` first (doc'd 2026-08-03: it records each agent's actual return value), then the transcript tail (`agent-<id>.jsonl` last records: trailing tool_result + no end_turn = cap kill) and re-dispatch with SMALLER SCOPE or an uncapped/default agent — same prompt re-dies identically while looking random; (c) have heavy agents Write their report file EARLY (skeleton, updated as they go) so a kill leaves evidence; (d) statusOf caveat: `STATUS: ERRORS_REMAINING: 0` is CLEAN — match count-0 before the generic pattern; (e) reviewer feedback prompts must reuse the REVIEWER'S OWN labels (flat numbered file:line) — never re-map to orchestrator lane names.

### Rule 12 sub-note — a control-flow regex over agent prose is an EXACT-TOKEN grammar, unit-asserted before launch (moirai effort #1: 1 returned run + 3 wasted fix dispatches)

Rule 12 fixes the classifier's BUCKETS and rule 10 asserts fan-out COVERAGE; both PRESUME the regex under them parses. This is the authoring rule they presume, and it binds EVERY regex whose result changes what the script does next — STATUS, `failedLanes` routing, INTEGRITY detection, phase-advance tokens. Three obligations, author-time, pure JS inline (rule 7):

1. **Anchor the token — never substring-match.** `/INTEGRITY:/` matched the verifier's own CLEAN report *"INTEGRITY: none found."* and RETURNED run 1 (`team-session/20260904-moirai-effort-1/build-state.md:21`). The exact-token form that effort shipped mid-run (`team-session/20260904-moirai-effort-1/plan.workflow.js:47`) is ITSELF defeated: it put `\s*` OUTSIDE the negative lookahead, so when the lookahead rejects at `none` the engine backtracks `\s*` to zero width, re-evaluates the lookahead at the space, and `**INTEGRITY: none found.**` MATCHES — the exact false positive it exists to reject (found 2026-09-10 when an e2 pre-launch assertion refused to launch, `team-session/20260910-claude-teamkit-followons/build-state.md` D-5; hit independently in `team-session/20260904-nzb-backend-orchestration/build-state.md:200-210`). Working form — whitespace and bold markers INSIDE the lookahead, so nothing outside it can backtrack past the guard; the negative counts only when the WHOLE clean phrase is TERMINATED by `.`, `!`, a bold close or end of line; and a marker line that carries a SECOND `INTEGRITY:` token anywhere later on that SAME line is a finding whatever precedes it: `/^[\s*]*INTEGRITY:(?:(?![\s*]*(?:none(?:\s+found)?|n\/a|no\s+(?:issues|findings|problems)(?:\s+found)?)\s*(?:[.!]|\*\*|$))|.*INTEGRITY:)/im`, canonical as `hasIntegrity` in `references/stage-templates.js`. Never key the negative on a LEADING WORD: `(?![\s*]*(?:none|no|n\/a)\b)`, shipped by e2 F-2 attempt 1, read the real findings `INTEGRITY: no test covers the new refusal — decoration`, `INTEGRITY: no-op guard: deleting it leaves the suite green` and `INTEGRITY: none of the suppressions were removed — gamed gate` as clean — false cleans on the integrity gate (`team-session/20260910-claude-teamkit-followons/build-state.md` PD-3). Anything ambiguous (`INTEGRITY: none found — but …`) FAILS CLOSED as a finding: a false BLOCK is visible, a false clean is not. The same-line alternative (`.*INTEGRITY:`) exists because e2 F-2 attempt 2's line-anchored-only form read `INTEGRITY: none. INTEGRITY: contract file edited by a coder` as clean: a terminated clean phrase hid the real finding packed behind it on one line (`team-session/20260910-claude-teamkit-followons/build-state.md` PD-4, from `team-session/20260910-claude-teamkit-followons/reviewer/review-1.md` Warning 1). Its cost: a clean line that quotes the token a second time fails closed. **Residual false cleans no line regex can see:** `INTEGRITY: none. ### Rule 6 sub-note — `resumeFromRunId` + caching semantics

Capture each launch's `WorkflowOutput.runId` and, after a **partial** run (some stages done, one crashed/rate-limited/timed out), prefer **resuming** over a cold relaunch: pass the prior `runId` as `resumeFromRunId`. Completed `agent()` calls whose inputs are UNCHANGED return cached — the run skips re-paying for already-finished stages and picks up at the failed one. Re-launching cold re-runs everything (live this audit: a cold relaunch re-ran ~72 agents).

`resumeFromRunId` is the within-session incremental-cache mechanism that backs rule 6. Use it for: the bounded reject→re-dispatch review loop and any single within-session multi-stage run that partially failed.

**Mechanism (documented): the cache is the longest unchanged PREFIX of `agent()` calls** — everything from the first changed call onward re-runs, changed or not. That explains both probe results (`wf_1d2dd417-323`): byte-identical args + script = 100% hit (nothing breaks the prefix); ANY `args` change re-ran ~70% (the first arg-interpolating prompt breaks the prefix, everything after re-runs regardless of its own inputs). **Implications:** resume is a real cost-saver ONLY when you re-pass IDENTICAL args (the resume-args contract below); surgical "only the changed stage re-runs" holds only when the edit sits AFTER the last cached call — never edit a stage EARLIER than the last cached call and expect downstream hits. So for the reject→re-dispatch loop: keep `args` and every SHARED prompt block byte-identical (prior prefix stays cached), and vary ONLY the contested stage's prompt — an `[attempt N]` / evidence-round tag, or an arg interpolated into that stage's prompt alone. A contested stage whose prompt does NOT change is not re-run — it replays its prior failing result from cache.

**Thread the `runId` — don't just document it (gaps-1).** Two threading levels: (a) WITHIN one workflow run the engine already caches completed `agent()` calls, so the in-script reject→re-dispatch loop costs nothing extra for unchanged stages; (b) ACROSS launches — when a re-dispatch crosses a human gate and becomes a SEPARATE `Workflow` launch — the orchestrator MUST keep the prior run's `WorkflowOutput.runId` (captured at step 4) and pass it as `resumeFromRunId` on the relaunch. Skip that and every prior passing stage re-runs from scratch. Treated as same-session-only until re-probed (banner probe-only list).

**Do not oversell it — treat `resumeFromRunId` as same-session-only until re-probed.** Probed same-session-only 2026-06-05, but the docs state no session restriction and the journal + script persist on disk — re-probe cross-session resume on the current binary; until then keep the durable `team-session/` artifact/marker as the cross-session checkpoint. The cache discount also depends on inputs being identical: if a resumed stage's prompt/`args` changed, that stage (and everything downstream of it) re-runs — see the resume-args contract below for the failure mode when `args` drift.

**Cache-safe prompt editing on resume (proven over 4 resume rounds, mono-cal P5).** When a resume must change ONE stage, edit ONLY that not-yet-run stage's prompt and keep every SHARED block **byte-identical** — the cache key is the RENDERED prompt text, so a shared-block edit re-renders every prompt in the script and re-runs the paid stages that already succeeded. Concretely, what worked: the shared `COMMON` preamble was never touched after launch, and a per-slice `rulings` field was rendered as an **empty string** for already-run slices so their prompts stayed byte-identical while the new slice's ruling text landed. That kept every completed stage cached across four rounds and avoided re-spending the calibration stage (~0.69 USD) and three paid errands three times over. The failure mode is silent and expensive — nothing warns you; you just pay again (`learnings.md` §5.2).

### Rule 6 resume-args contract — RE-PASS THE SAME `args` ON RESUME (reliability-9)

**When you resume with `resumeFromRunId`, you MUST re-pass the exact same `args` you launched with.** `resumeFromRunId` resumes the *journal*, NOT the `args` — omit them and every arg-interpolated global (`SESSION`, `PKG`, `DOC_URLS`, …) comes back `undefined`. This fails SILENTLY and is doubly destructive:

1. **Full cache miss.** The cache key is the rendered prompt TEXT. Every `agent()` prompt that interpolated an arg now renders differently (the arg reads `undefined`), so EVERY prompt changes → nothing cache-hits → the whole run re-pays from scratch. (Hit live this audit: a resume with dropped `args` re-ran ~72 agents instead of cache-hitting, ~5M tokens re-spent.)
2. **`undefined`-path writes.** A `Write` target built as `` `${SESSION}audit-report.md` `` renders `undefinedaudit-report.md` → files land at the REPO ROOT as `/repo/undefined*` instead of inside `team-session/`. No error is raised — the run looks like it succeeded.

Neither failure throws. Treat re-passing identical `args` as part of the resume call, not an optional extra. Same rule for the post-gate relaunch in step 4 and the reject→re-dispatch loop: if you thread the prior `runId`, thread the prior `args` with it.

**Guard at the top of every script (fail-loud).** Args can also go missing on a fresh cold launch (typo'd `args` key, wrong invocation). Add the top-of-script args guard — canonical impl in `references/stage-templates.js` — so the run aborts with a clear error instead of silently writing to `/repo/undefined*`.

## Single-branch write model (verified)

Clobber risk is **same-FILE** writes, not parallel writes. Three write types:
- **Schema returns** — not files; always parallel-safe.
- **`team-session/` artifacts** (each agent → its OWN path, e.g. `coder-X/progress.md`) — parallel-SAFE (disjoint paths never collide; spike 4 confirmed concurrent writes).
- **Source edits** (`packages/...`) — the only constrained case:
  - disjoint file-ownership → parallel OK, **but PROVE it first**: run the `disjoint(owners)` glob pre-flight (rule 14, reliability-7) before the fan-out — the planner's "non-overlapping globs" is discipline, not a runtime check, and no hook fires for workflow writers. Any pairwise overlap → halt or downgrade to single-writer (a stray out-of-lane agent clobbering a peer is otherwise UNDETECTED).
  - **single-writer** (serial pipeline, one source-writer at a time) — default, safe; also the auto-downgrade target when the disjointness pre-flight flags an overlap.
  - **propose-then-apply** — parallel coders WRITE a unified-diff patch to `<session>proposals/{name}.diff` (FILE handoff — robust vs schema diff-fidelity); ONE sequential apply stage reads the patches, applies disjoint ones + flags same-file collisions. Parallel reasoning, serial mutation.

**A DIRTY tree at launch is the normal case — snapshot it, or every later diff lies.** Rule 5 bans
worktrees, so a run starts on whatever the branch already carries, and a concurrent session's
uncommitted work may sit on the very files this run must edit (measured 2026-08-23: it did). Before the
first write, `git diff -- <scoped paths> > <session>baseline.diff`, and tell EVERY stage to subtract it
before claiming any hunk as this run's. Without it, reviewers review a peer's work, gate-gaming audits
flag a peer's suppressions, and "additions only" is unprovable. **Ban `git checkout` / `restore` /
`stash` / `reset` / `commit` in every dispatch** — an agent "restoring" a deliberately-broken file with
`git checkout` destroys uncommitted work it does not own. To undo an edit, RE-EDIT the file.

**An AC whose reference point can MOVE must name a baseline SHA, not `HEAD`.** Same root as the dirty
tree: the run does not own the branch. Record `git rev-parse HEAD` at t0 in `build-state.md` and grade
every freeze / "byte-identical to" / diff-scoped criterion against THAT sha — `HEAD` at grade time is a
different commit than `HEAD` at seal time whenever a concurrent session, or the nightly backup commit,
lands mid-run. (Measured 2026-08-24: AC-5 froze a doc set *"byte-identical to HEAD"*; `fb701c9c2` landed
mid-run from another session — this run never commits. A freeze measured only against a moving HEAD moves
WITH it: the criterion reads green even if that commit rewrote a frozen file. The lead re-measured
`git diff <t0-sha> HEAD --stat -- <frozen set>` → empty and the freeze held, but nothing in the contract
required that measurement.) If a sealed contract already says `HEAD`, grade BOTH and record the t0
comparison as the one that means anything — an orchestrator ruling, not a contract edit.

**Order the guard before the surface it guards.** When a run ships both a capability and the check that
makes it safe, build the check FIRST — never leave a window where the capability is reachable unguarded,
not even within a single run. If the plan's own stage order puts the surface first, invert it and say so.

**Cite repo-root-relative, always.** A bare `src/cli/foo.ts:41` or `store.ts:168` is ambiguous the moment
a monorepo has two of them, and it strands the next reader. Measured twice on one effort, two authors
apart. Every `file:line` in a `team-session/` artifact or dispatch is relative to the repo root, or it is
a defect — including in prose you are only quoting.

**Contract is immutable to writers.** No coder/tester may edit `definition-of-done.md`, `requirements.md`, `team-plan.md`, or weaken a gate config to pass — the finalize gate-gaming guard treats any such edit as a FAILED gate. The contract is graded, never edited, by the things it grades.

## Measurement — exercising the running product (COMPOSE → MEASURE → DISPOSITION)

Every gate above reads BYTES: lint/types/knip/test over the source, reviewers over the diff, the validate loop over each AC's verify command, grade over the record. None of it ever runs the PRODUCT. Three stages close that gap, composed AFTER the validate loop (the last coder fix has landed — compose earlier and you compose against bytes a later round replaces) and AFTER grade — hash-bound dependencies are selected at a SEAM BEFORE the launch that consumes them (`references/execution-evidence.md` §2), so nothing written in a segment can reach THAT segment's grade deps or its grade-inputs snapshot: the grade never finds its own, at any position. Measurements therefore feed the NEXT grade attempt (below, and Procedure step 6), and sitting after the grade is also what lets DISPOSITION read the grade record:

| Stage | Does | Shape |
|---|---|---|
| **COMPOSE** | builds the real journeys from what is ACTUALLY on disk — the create-side verification approach is a suggestion authored before the build, never the manifest — and records the delta | ONE serial stage, `gate()`d: a compose failure has nothing to fan out |
| **MEASURE** | exercises each journey and records input and output VERBATIM | `parallel()` fan-out → `auditEmpty` → `retryMissing` → `coverage`, like every other fan-out (rules 10, 15) |
| **DISPOSITION** | correlates the records into the index grade reads; routes prod-gated journeys to the human checklist | ONE serial stage; its output is what the orchestrator selects into `runtime/grade-inputs-{n}.md` |

**What the escape hatch is actually worth — state this honestly or the lane inherits this system's whole defect history, claims outrunning what was measured.** `NEEDS_HUMAN_EVIDENCE` was written when the sandbox could render nothing, and for most surfaces that is now too pessimistic: **HTTP endpoints, CLIs, package scripts, DB rows, queue depths, files and logs are exercisable TODAY, in-workflow, with Bash alone.** For those, parking is the RESIDUE after a measure pass cannot reach a surface — never the first answer to "this one needs a running system".

**Rendered-UI journeys are the exception, and they are PROD-GATED today.** Two independent blocks, either one sufficient: (a) MCP reaches a custom agentType ONLY through frontmatter `mcp__*` globs (rule 2) and `team-measurer` **declares none** — so no MCP server projects into it, including the Playwright one that IS configured user-level (`~/.claude.json` root `mcpServers`; reading of 2026-09-12, and a configured server a role cannot address is not a capability); (b) a LIVE `spyglass` is **paid and human-gated**, which `## Prod-gating` forbids inside the autonomous workflow regardless. ### Measurement is not verification — the rule an author must not get wrong

> **Never ask a measurement agent whether something worked.**

You cannot prompt an agent out of sycophancy. *"Did checkout work?"* comes back yes regardless — and that is only a problem because an OBSERVER was asked for a VERDICT. So never ask one. A measurement agent is asked to exercise a surface and **record input and output verbatim**: the HTTP status and body, the page text, the row id, the CLI stdout and rc, the screenshot path. It emits no PASS, no FAIL, no *"works correctly"*. Judgment happens later, in a DIFFERENT agent, reading the record.

This is not a new doctrine, it is the existing one pointed at a live surface — `references/execution-evidence.md` §2 (the WORKER does the read/hash/compare; an INDEPENDENT reviewer decides acceptance) and §6 (raw and normalized stay separate; reporting only the normalized form is refused). Cite those in the prompt you author; never re-derive them here.

**The STATUS-line trap.** Every dispatch closes with a terminal STATUS line, so a measurer has one too — and it reports whether the MEASUREMENT completed, never whether the product works:

| Line | For a measurer it means |
|---|---|
| `CLEAN` | I exercised the surface and recorded what I observed |
| `ERRORS_REMAINING: <n>` | I could not complete the measurement — surface unreachable, tool failed |
| `BLOCKED` | the environment or a precondition was not there |
| `PARTIAL` | I measured some of the assigned surfaces and recorded which I did not |

**A measurer that writes `CLEAN` because "the feature worked" has misunderstood its job and reintroduced the verdict** — an HTTP 500 recorded faithfully is `CLEAN`, and a journey that never ran is not `CLEAN` however healthy the product looks. State this explicitly in every measurement prompt you author: it is the single most load-bearing sentence in this section.

### Four things every journey declares

| | Requirement | Why |
|---|---|---|
| **artifact, never the claim** | the record carries the capture path, the bytes, the row — raw first, derived second | *"I verified the order was created"* is a claim; the row id and the response body are evidence (`execution-evidence.md` §6) |
| **negative control** | exercise the journey in a state where it MUST NOT succeed, and record that it did not | a journey that passes against a dead server is indistinguishable from one that works. Same instrument as the finalize decoration check — break the guard, confirm RED |
| **correlation handle** | a request id / order id / timestamp window carried through every observation of ONE transaction | without it, concurrent agents watching one transaction from three sides produce three anecdotes nobody can reconcile |
| **prod-gating side** | declared in COMPOSE, per journey | `## Prod-gating` is NOT relaxed by a journey needing it: deploys, migrations, deletes, kubectl mutations, scaling and paid live calls never run inside the autonomous workflow. Read-only exercise of a live surface is AFK; anything that mutates or spends leaves as a human-gated checklist row |

### Deviation is an OUTPUT, not a failure

The create-side approach is authored BEFORE the build, so it cannot know what was built. COMPOSE composes the journeys from what exists on disk and RECORDS the delta — a suggested journey with no surface behind it, a surface nobody suggested, a renamed route. **A compose stage that finds the suggestions stale is doing its job.** The delta is a recorded deviation, not a defect to reconcile away — and `map.md` still bounds it: a journey into **Out of scope** or past the destination is a human call, not a compose decision.

### Measurements FEED grade — they do not gate it

DISPOSITION's records reach grade as dependency references (`{taskId, attempt, resultPath, sha256}`) selected into `runtime/grade-inputs-{n}.md`, which `GRADE_PROMPT` already requires non-empty. Nothing in grade's read-set changes — but they ride the DEDICATED `args.gradeDeps` channel, **never** the shared `args.deps` every other heavy stage reads. Procedure step 6 carries the full recipe and the two hazards it closes.

**It is the NEXT grade, and reaching it is an ORCHESTRATOR act — the loop does not close itself.** DISPOSITION recommends; it never branches the script (that would hard-gate the run through the back door). A disposition saying a measurement would change a grade is an instruction to relaunch, and the canonical recipe is **Procedure step 6**. Skip it and this whole lane is write-only: the records land on disk and no grade ever reads them.

**Never pass the MEASURE fan-out result to `gate()`.** `gate()` stops the run on anything not clean and `statusOf` classes PARTIAL as `errors`, so gating there turns "a journey observed a 500" into a halted run and hands the measurer back the verdict this section exists to take off it. Gate on measurement COMPLETENESS only — COMPOSE produced a manifest, DISPOSITION's record set is complete (`coverage()` over the fan-out, as always). What the journeys OBSERVED is grade's to weigh.

**A measure round is a ROUND, never a coder fix DISPATCH.** A measurer is not a coder and fixes nothing, so it never charges the global fix ceiling — that unit is one ACTUAL dispatch of a coder (`## Autonomy contract` → *Two accounting units*). Bound the phase with its own per-phase round cap, seeded from the ledger like every other; ONE round is one full fan-out, not one per journey (per-slice bounding is `auditEmpty` / `retryMissing` / `coverage`).

## Orchestrator rulings (`PD-n`) — adjudicating plan-vs-reality without breaking the seal

The contract is immutable to writers (above). That does not say what happens when execution proves the CONTRACT wrong — and the only remaining moves are bad ones: edit the contract (destroys the seal; writers editing what grades them is the exact failure the contract exists to guard) or halt the effort. The third move, proven over one effort (PD-15..PD-19):

> the orchestrator **rules in writing** → the **contract stays UNEDITED** → the ruling is graded as a **recorded deviation** whose intent-preservation an independent grader **re-verifies**.

What it handled in practice: a mechanical gate failing on a foreign, pre-existing error in another package (amended to *"zero errors attributable to `<owned glob>`"* after the orchestrator reproduced it standalone, and forbade both remedies that would have mutated a frozen lockfile); a byte-freeze whose own frozen file made the criterion **unsatisfiable** (deviated +5/−0, three job names byte-unchanged, checks then went green); a gate-gaming remedy rejected in favour of a real surface reduction; and twice, a verdict the orchestrator had **already signed** being corrected against new measurement.

**The argument against is real and is not buried here.** It concentrates authority in one agent. Two of the five rulings corrected an earlier ruling by that same agent — healthy — but **nothing forced that review**; the orchestrator happened to re-measure. A ruling that is wrong and unchallenged is worse than a halt: a halt is visible, a bad ruling gets laundered into the record as a legitimate deviation.

**Judgement: formalise it, bounded.** The authority already exists de facto — the orchestrator is the thing that decides whether execution proceeds — so writing it down adds no power. What it adds is a mandatory written trail and a mandatory independent re-check on a decision that otherwise gets made silently. Unformalised, this same call still happens; it just leaves no evidence.

Mandatory content — a "ruling" missing any of the four is not a ruling, it is an unrecorded deviation:

| | Clause |
|---|---|
| a | the **measurement** that forced it — command + observed rc, or `file:line` |
| b | the **alternatives considered and why each was rejected** — name the forbidden ones explicitly (e.g. a remedy that would mutate an artifact another AC freezes) |
| c | what the ruling **does NOT license** |
| d | a **grader instruction to re-verify the INTENT** rather than accept the ruling — a ruling is not settled until an independent grader re-measures the intent it claims to preserve |

Under the opt-in evidence/applicability protocol a ruling that touches a **premise** carries three more
references **on that same row** — same ledger, no second one: the affected `P-*` ids + the exact task and
AC consumers + the exact affected attempt records; the change classification it asserts (create's
existing table, never a new one — see the seam row below); and, for anything paid, irreversible,
restorative or outside existing authorization, the exact authorization locator with its target and
ceiling. Absent that locator the ruling does not license it. `references/execution-premises.md` §10.

Two addenda, both measured 2026-08-23:

- **Authorise the CLASS, not the instances.** A ruling that enumerates specific sites (`file.ts:181/184/186`)
  re-blocks the moment an equivalent site turns up that the list did not name — it happened twice on one
  effort, costing two extra rulings. State the principle and its limit (*"…may be EXTENDED additively; no
  existing expectation weakened, removed or skipped"*), then let it cover every instance.
- **A conversational grant is recorded exactly like a ruling.** "You have my auth" against a multi-item
  report is ambiguous, and an unrecorded reading is an unauditable deviation the moment anyone disagrees
  — the failure this effort's own PD-21 records. Write the four clauses, state the reading so it is
  FALSIFIABLE, and enumerate what it does NOT cover. **A blanket grant never authorises a paid or
  irreversible run** — those need per-run authorisation naming target and ceiling.

Out of a ruling's reach — these escalate to the human gate, never adjudicated:
- anything that lowers a blocking AC's **intent**. The LETTER may bend where the letter is self-contradictory; the intent may not.
- anything in `map.md` **Out of scope**, or that moves the **destination**. (The last ruling in that run found a blocking AC architecturally unreachable and routed it to the NEXT effort rather than narrowing the destination to fit — that is the correct shape.)
- any **material** change to `definition-of-done.md` / `requirements.md` / `team-plan.md` / `design.md` / `map.md` — a delta outside existing authorization (outcome, scope, tradeoff, exclusion, acceptance threshold, cost/external action, autonomy). That is a human decision, not a ruling. **Classify with the EXISTING table before escalating** — `team-kit-create/references/approval.md` → *Classify changes before asking*; this skill adds no second classification and no second gate. Identical content reuses the recorded approval; an editorial change with an unchanged claim is recorded, reconciled and **revalidated** (every edit stales its hashes, and a changed acceptance contract is regraded — never relabelled with new hashes) without a new user decision; only the material delta is presented, alone, and waits. **A weakening is never editorial**: removing or narrowing an AC, an obligation, a gate, a premise or a consumer set is an acceptance-threshold change whatever it is labelled (`references/execution-premises.md` §9). Orthogonal, and unchanged by any classification: **an agent graded by a file never edits that file** — writers (coder/tester/reviewer/verifier/grader) touch none of these five, and doing so is an INTEGRITY finding routed to the human. The classification decides whether a needed change needs the user; it never decides who may write.

**When you assemble a brief FOR that human decision, give it an adversary** — the same optional-but-named
shape as the FIDELITY CHECK below, and for high-stakes escalations treat it as required. A single
research agent writing the brief has a structural incentive toward whichever verdict unblocks the work,
and it does not need to fabricate anything to act on it: it simply builds one side at length and gestures
at the other. Measured 2026-08-23 — the brief was accurate to the byte and still posed a **false binary**;
the second agent found two more options, and **the human chose one of those**, not the brief's
recommendation. A one-agent decision brief is advocacy with citations.

Where they live: `<session>build-state.md` under **Orchestrator rulings**, ids `PD-n`, cited by the validate stage's per-AC grading and by the final verdict. Same ledger as the AC state — re-read it at every gate, don't trust recollection.

## Autonomy contract — where humans sit, and where they don't

Plan approval (create Step 7) is the act that GRANTS autonomy; after it, the run self-drives to its stop condition. The plan's `autonomy:` block (authored by `team-planner`, ratified at create Step 5) is the grant's terms — loop caps, escalation set, seam policy. Softening a plan-declared gate run-side is editing a ratified contract: never do it. Absent an `autonomy:` block (direct-task mode-2), these defaults apply.

**Humans sit at exactly these seams — nothing else stops the run:**

| Seam | Why human |
|---|---|
| plan-declared `type: HITL` tasks + the prod/paid/irreversible checklist | genuinely destructive / one-shot |
| `STATUS: BLOCKED` / `NEEDS_CONTEXT` anywhere, after triage fails (Triage-first below; an INTEGRITY / budget / agent-cap BLOCKED or a plan-declared direct gate skips triage) — EXCEPT a Codex-lane worker whose `outcome.json` reads `"channel": "transport"`, which auto-falls-back to the role's Claude twin, notify only | "the plan is wrong / I'm missing context" and one fresh assessor could not resolve it; a Codex worker's `"channel": "semantic"` BLOCKED takes this same route |
| a **material** contract-file delta (outside existing authorization), anything touching `map.md` Out-of-scope / destination, a premise strike that reopens a ratified decision | scope is the user's. Classify FIRST with the existing table (`team-kit-create/references/approval.md` → *Classify changes before asking*) — identical / editorial / in-authorization-method changes are recorded, revalidated and notified, not asked; a weakening is material by definition, never editorial (`references/execution-premises.md` §9). This gates the CHANGE, not the writer: no writer edits a contract file at all (INTEGRITY row below) |
| INTEGRITY findings (gamed gate / contract edit / decoration guard) | never hand these back to the coder that produced them |
| cap / global-ceiling exhaustion, incl. a same-failure stall on a loop's final round (a stall with rounds left is a triage trigger — Triage-first below) | bounded retries spent — arrive with the ledger, not a first-error stop |
| a paid run's second attempt | "a second run is a decision, not a retry" |
| parked `NEEDS_HUMAN_EVIDENCE` ACs | evidence no measure pass could reach — parked AFTER measurement, never instead of it (`## Measurement`) |

**Triage-first (BLOCKED / NEEDS_CONTEXT / stall).** Before one of the trigger stops below reaches the human, the orchestrator dispatches one fresh TeamKit agent fitted to the blocker to assess it. The human is escalated only when triage fails.
- Trigger set: `STATUS: BLOCKED` / `NEEDS_CONTEXT` from any stage (not INTEGRITY-flagged) + a same-failure stall stop (no progress, rounds left). These keep their human gate: round-cap / fix-ceiling exhaustion, budget-throw or agent-cap BLOCKED, INTEGRITY, material delta / Out of scope / premise strike, paid second attempt, `NEEDS_HUMAN_EVIDENCE`.
- Agent selection: NEEDS_CONTEXT → `team-researcher`; BLOCKED design/plan conflict or ambiguity → `team-architect`; BLOCKED scope / contract question (review finding beyond recorded scope, unsatisfiable AC) → `team-plan-reviewer`; stall → `team-investigator`. The assessor walks the FRAMEWORK ladder (STATUS Protocol → BLOCKED) and never edits source.
- Resolved means: the assessor recommends; the orchestrator records a `PD-n` inside a ruling's reach and relaunches with changed inputs. Triage attempts per blocker: 1. Triage failed = the assessor returns BLOCKED / NEEDS_CONTEXT, or the fix needs a change outside a ruling's reach, or the same stage stops the same way after the relaunch.
- Human fallback: the human receives the blocked agent's STATUS line + report path, the triage record, and a decision brief with an adversary (`team-kit-run/SKILL.md` → escalation briefs; "arrive with the ledger").
- Triage never decides what already needs a human: a material contract delta, destination / Out-of-scope change, paid or irreversible authority (`approval.md:21`; `SKILL.md:339,342`).
- Codex lane: same route. A root-recorded triage ruling may authorize one `resolution` attempt after `blocked` / `needs-context`; a repeated-signature (no-progress) resume stays user-only.

**Route on the tag.** Every stop the script returns names its route in additive fields: `route` (`triage` · `human`), plus `trigger` (`blocked` · `needs-context` · `stall`) and `assessor` on a triage stop, or `gate` (`round-cap` · `fix-ceiling` · `budget` · `agent-cap` · `integrity` · `paid` · `needs-human-evidence`) on a human one. **Streak refinement of "per blocker".** A blocker is bounded per stage streak: once a stage has used its triage, a second stop in that streak — no pass between, even for a different reason — goes to the human with the triage record. BLOCKED breaks never consume a round, so round caps alone never end a chain of distinct blockers.

A stage with an open `triage:` row has used its triage.

**Seeding after a changed-args relaunch.** Seed `roundsAlreadySpent` for the loop whose prefix broke with every round of it that earlier segments consumed, and `fixesAlreadySpent` with every fix dispatch they consumed. A replayed round may be counted twice; that only removes headroom — a seed never raises a cap.

**Assessor dispatch.** The assessor gets the blocked STATUS line, its report path, the relevant ledger rows and read access; it never edits source, writes `<session>{role folder}/triage-{stageKey}-{k}.md` (folder = role name without `team-`), closes THAT file with its terminal STATUS line and returns the same line (close-the-artifact, below). Its recommendation binds nothing until the orchestrator records it as a `PD-n`.

**Everything else the orchestrator handles itself, notifying instead of asking:** re-dispatch/continue decisions between runs (relaunch with `resumeFromRunId` + identical args); ONE auto-resume on a `transport:`-marked failure (rule 11); one single-slice retry on a true coverage gap — **only under a RetryPermit it recorded after reconciling the journal ITSELF** (the script cannot read `journal.jsonl`; never a paid slice, never a user skip; no permit → the helper HOLDs and the orchestrator reconciles, `references/execution-premises.md` §7); recording a premise state change and holding exactly its **named** consumers while unrelated eligible work continues (§6 — a strike that reopens a ratified decision still goes to the human); glob-overlap auto-downgrade of the colliding pair to single-writer (rule 14 already sanctions it; recorded as a deviation); Codex `channel === "transport"` auto-fallback to the role's Claude twin (verdict recorded as `claude-fallback` in build-state, notified — never presented as a Codex verdict; the human re-enters only if cross-vendor independence was the point of the opt-in); splitting an oversized plan into chained sequential launches within the plan's approved roster (cumulative agent count never exceeds what the plan enumerates); dispatching the one triage assessor for a `route:'triage'` stop, recording its `PD-n` and relaunching it (Triage-first above).

**Bounds that make the grant safe:** all counters live in `build-state.md` and RESUME across relaunches; a same-failure-signature stop ends a no-progress loop immediately in every phase loop (review, verify, validate); the global fix ceiling bounds coder dispatches; the `/workflows` kill switch and the 1000-agent lifetime cap stay as runaway backstops. `budget.remaining()` guards a loop only when the user set a token target (`budget.total` non-null): it counts output tokens spent this turn — main loop and every workflow, one pool — and returns `Infinity` without a target. Never count it as a brake. The run's job is to arrive at its human gate either CLEAN or with a fully-diagnosed, ledger-recorded residue.

**Two accounting units, and they are NOT interchangeable** (this is the canonical statement; rule 12, Procedure 5 and entry-mode-1 step 1 point here and do not restate it):

| Unit | What one charge is | Cap and its scope | Script counter |
|---|---|---|---|
| **Review round** | one remediation ITERATION of one phase loop — the loop takes another turn | **per phase**, and each phase has its OWN cap: review / verify / validate, defaults 10 / 10 / 10. Review rounds never consume verify rounds | `MAX_REDISPATCH` / `MAX_VERIFY` / `MAX_VALIDATE` vs `attempt` / `vRound` / `aRound` |
| **Coder fix dispatch** | one ACTUAL dispatch of a coder to fix something (`impl-redo`, `fix-mech`, `fix-ac`) | **one global ceiling** across review + verify + validate, default 30 | `TOTAL_FIX` vs `spendFix()` |

They diverge in both directions, which is why one number cannot stand in for the other: one round can carry **two** distinct repairs (a test repair and a runtime repair) — that is two dispatches against the global ceiling and still ONE round, never two fabricated rounds; and a round that finds nothing to hand a coder charges **zero** dispatches (a no-op correction is not dispatched and not charged). Caps come from the plan's ratified `autonomy:` block; the run spends against them, it never sets them. A ledger resumed from a launch that ran under the lower pre-D-7 template defaults gains the raised headroom; its seed is still a consumed count, never a cap.

**On resume, consumed history is SEEDED — never reset, and seeding never expands a cap.** In-memory counters die at every relaunch, so both units are seeded from the ledger through `args.autonomy` (`roundsAlreadySpent` per phase, `fixesAlreadySpent` global — args interpolated into NO prompt, so they do not break the cache prefix). Three rules make the seed safe:

- **A seed only ever REDUCES remaining headroom.** It is a consumed count, not an allowance. A seed at or above its cap means the next dispatch in that lane is **REFUSED** — the run returns its residue to the human gate with the ledger. "Seeded to the cap" is never "one more round granted", and no seed may raise `TOTAL_FIX` or a round cap: raising a ratified cap run-side is editing the autonomy grant.
- **Seed only the charges this segment will not re-incur.** A `resumeFromRunId` relaunch with identical args re-executes the script from the top and replays completed `agent()` calls from cache (rule 6) — the in-script counters re-increment as it walks back through those rounds. Charges from THIS run's own replayed rounds are therefore already re-counted in-script; seed the charges from EARLIER launches only, or the same fix is charged twice. (Derived from the documented resume-caching contract, not from an observed run — check it before trusting the arithmetic on a long chain of segments.)
- **`build-state.md` is authoritative; the script counter is a bounded mirror.** The orchestrator writes both units back after every round, with their prior values (`design.md` Evidence Schema build-state row). A disagreement between the two is resolved toward the ledger — never by taking whichever number leaves more headroom.

## Procedure (orchestrator)

1. **Triage the task** against the rules: which parts are read-only (parallel-safe), which are source-writes (serialize/propose-apply), which are prod (gate out), and which are **paid / irreversible / one-shot** — those get a preconditions manifest + a calibration gate ahead of them, and a one-run-per-dispatch clause in the dispatch itself (see the paid-stage section above). Triage one more axis: which claims are only true of the RUNNING product — those are exercised by COMPOSE → MEASURE → DISPOSITION after the validate loop, never settled by a reviewer reading the diff (`## Measurement`).
2. **Seed team-session** (optional but preferred for traceability): `mkdir team-session/{YYYYMMDD-slug}/`; write `prompt.md` (raw task). **Snapshot the dirty tree NOW**: `git diff -- <scoped paths> > <session>baseline.diff` — the FINISH/FINALIZE/fix prompts all subtract it, and without it every later diff lies (single-branch write model above). Pass the absolute session path into agents. **If the plan declares the evidence protocol** (opt-in — legacy workflows are not migrated): RESERVE each stage's attempt in `build-state.md` *before* any dispatch and pass the epoch + per-task attempt numbers in `args` — obligations, path grammar and record fields in `references/execution-evidence.md` §1–§5. Snapshotting and reserving are preparation; neither is evidence that a stage ran. **If the plan declares a premise** (it does so only where execution actually depends on one), open its row in that SAME `build-state.md` before the dispatch that consumes it — `P-*` + linked decision, domain owner, acquisition producer, the exact task and AC consumers, subject, predicate, the **sourced** freshness/applicability policy (no invented threshold; no source ⇒ `unresolved` ⇒ its consumers are held) — `references/execution-premises.md` §2, §4.
3. **Author the workflow** by composing the stage templates below. The script MUST open with the pure-literal `export const meta = {name, description, phases}` block (platform requirement — the lint checks it, but mode-2 skips the lint, so author it in); `phase()` titles match `meta.phases` EXACTLY — enumerate every phase any inlined helper emits (Audit/Propose/Preflight/Calibrate/Finish/Grade included). Add `whenToUse` to any script destined for save as a `/command`. Use `phase()` per stage; set `opts.phase` inside `parallel`/`pipeline` — and prefer `pipeline()` for per-lane multi-stage chains (research→implement→verify per disjoint lane): it is the documented default, no barrier, wall-clock = slowest chain; the null-drop of a thrown stage is the same silent-gap vector rule 10 guards, so coverage() applies to pipeline results too. A recurring gate cluster an existing saved workflow already implements can be invoked as a CHILD via `workflow('name', args)` (one nesting level; shares budget/concurrency) instead of duplicating stages. Heavy stages return FREE TEXT + a disk artifact whose OWN last non-empty line is that same `STATUS:` line (rule 9 + close-the-artifact below); reserve `schema:` for LIGHT stages. Under the evidence protocol, wrap each stage prompt in `bindAttempt(...)` so the reserved output paths, the exact inputs to snapshot and the exact selected dependency terminals + hashes ride IN the prompt (`references/execution-evidence.md` §2 consumer duty) — a consumer resolving its input by directory listing or "latest" pointer is the defect this closes. Any paid/irreversible stage is preceded by the PRECONDITIONS gate and (for a one-shot) the CALIBRATE gate, each hard-returning on not-CLEAN. The ~15-agent ceiling is a LOCAL session guideline (gate granularity + cost), NOT a platform cap — documented platform limits are 16-way concurrency, 1000 agents/run lifetime, 4096 items/call. A bigger plan: chain sequential launches autonomously within the plan's approved roster (autonomy contract above), or raise the guideline via /config.
4. **Launch** via the `Workflow` tool (background). **Capture the launch's `WorkflowOutput.runId`.** For multi-gate work, run up to the next seam, then TRIAGE: a plan-declared human gate / paid / contract question, or a BLOCKED / NEEDS_CONTEXT / stall whose triage failed (or that the plan declares a direct gate) → present and wait; a `route:'triage'` stop → Triage-first (dispatch, `PD-n`, relaunch); anything else → relaunch the next segment YOURSELF and notify (autonomy contract above). Either way: stop the prior run first if still live (`TaskStop`), pass the prior `runId` as `resumeFromRunId` **AND re-pass the SAME `args`** so already-completed, unchanged `agent()` calls return cached (rule 6 + sub-note + resume-args contract). Dropping `args` on resume re-renders every prompt → full silent cache miss + `/repo/undefined*` writes (reliability-9). The reject→re-dispatch review loop is the prime beneficiary: thread the prior `runId` (with identical `args`) so only the changed implement/review stage re-runs, not the whole pipeline. **A genuine rerun, correction or regrade is the inverse case**: reserve a NEW attempt number first and pass it (plus a fresh grade tag) in `args`, so the prompt CHANGES and the stale verdict cannot replay cached — identical-args resume alone never makes changed evidence current (`references/execution-evidence.md` §1 A5). **Retain before you overwrite or relaunch** (evidence protocol): every REVIEWED script revision is copied to `<session>runtime/scripts/` with its SHA-256 first — `references/execution-evidence.md` §2 *Script revisions*.
5. **Update the build-state ledger + report**: write/refresh `<session>build-state.md` keyed on AC ids (pending/passed/failed/needs-human + grader + verdict) **plus the counters, each unit recorded separately with its prior value — per-phase review/verify/validate ROUNDS and the global coder fix DISPATCH count (they are seeded, not reset, on relaunch, and a seed never raises a cap — rule 12 → `## Autonomy contract` *Two accounting units*) — plus any `PD-n` orchestrator rulings with their four mandatory clauses**, rolled up from the finalize+validate artifacts — the orchestrator's externalized memory (re-read it each gate; don't trust recollection). Under the evidence protocol the same file (never a second ledger) also carries the attempt reservations and an explicit **current evidence selection** per consumer/AC, and the orchestrator captures an immutable `<session>runtime/grade-inputs-{n}.md` before each grade attempt — duties and non-goals in `references/execution-evidence.md` §2, §9. The same file also carries the **execution premise rows and their held consumers** (`references/execution-premises.md` §2, §12) — never a second ledger and never a second premise registry: `P-*` ids stay the ones `map.md` **Premises** minted. Keep the three questions apart in what you record: acquisition (did the measurement run — a CLEAN acquirer can report a REFUTED premise), domain comparison (what the value means), applicability (does it bind THIS consumer now). On a state change hold **only the named** consumers, retain every conflicting applicable observation (deletion is an INTEGRITY finding), leave completed effect receipts byte-unchanged, let unrelated eligible work continue, and reserve a FRESH grade attempt for each affected AC when support returns — §5, §6. Every minted id carries a human slug (`PD-4 amend-lint-scope`, `AC-3 gates-green`) — ids alone are unreadable at decision points (`team-session-writing` → Readable ids). Relay the structured result + team-session artifact paths **in chat, as file paths — never a published Claude Artifact (claude.ai/code/artifact link) unless the user explicitly asked for one this run.** Return the prod-gated checklist — incl. any blocking SEMANTIC AC marked `NEEDS_HUMAN_EVIDENCE` (distinct `needs_human_evidence` status, never conflated with failure) — for the user to run manually. The run is DONE only when every blocking AC reads `passed`.
6. **Close the measurement loop — relaunch the grade that will read the records.** A measurement cannot reach its own segment's grade (`## Measurement`), so measurements are worth nothing until an orchestrator carries them to the NEXT grade attempt; nothing in the script does this for you. Same shape as supplying evidence for a parked `NEEDS_HUMAN_EVIDENCE` AC (Output below) — one recipe, two triggers. When DISPOSITION names a record that would change a grade: write that record's path into its AC row in `<session>build-state.md`; **RESERVE** the next grade attempt and capture its immutable `<session>runtime/grade-inputs-{n}.md`, selecting each cited record as `{taskId, attempt, resultPath, sha256}` (`references/execution-evidence.md` §1 A2/A5, §2 — never by directory listing or a "latest" pointer, and never a transport-synthesized or reconstructed slice, which is recorded but never citable as a producer's terminal); then relaunch `resumeFromRunId` with the **SAME `args`** plus the new `attempts.grade` / `gradeTag` / `gradeDeps` selection. **Through `gradeDeps`, NEVER through `deps`** — `args.deps` is a single SHARED channel ELEVEN other heavy stages read (impl, spec, qual, finalize, fix-mech, validate, fix-ac, finish, compose, measure, disposition — FINISH joined the list when it was BOUND through `bindAttempt`, which interpolates `args.deps` into its prompt like every other bound stage; feeding the channel moves those bytes), so feeding the grade through it re-renders all of their prompts, misses the cache on every one (rule 6) and replays them onto their already-consumed reserved attempt paths, landing a second record on write-once bytes that `attemptRef`'s per-execution collision guard cannot see across launches; `gradeDeps` is absent-only-fallback, so an empty one is REFUSED rather than silently reverting to the shared list. **`gradeDeps` closes the shared-CHANNEL hazard and NOT the CACHE one — grade must also be the LAST `agent()` call in its segment.** Rule 6's cache is the longest unchanged PREFIX (`resumeFromRunId` above): a changed grade prompt breaks the prefix, so every call AFTER grade re-runs regardless of its own byte-identical prompt. In the one-script template the measurement lane sits after grade (compose → measure → disposition), so a naive re-grade replays all three — re-driving live surfaces, and, because this step bumps only `attempts.grade`, re-minting their already-consumed reserved paths (`measurer/verification-plan-1.md`, `goal-auditor/disposition-1.md`, each measurer attempt terminal) onto write-once bytes that `attemptRef`'s per-execution guard cannot see across launches. So author the lane as its OWN segment (step 4's multi-run seam) and let the re-grade segment END at grade. Bumping every lane seed instead removes the collision only by genuinely re-running the whole fan-out: that is a decision to re-measure, never a default. **FINISH is the same hazard from the OTHER side of the grade.** It runs BEFORE the mechanical gates, so no after-grade prefix break reaches it — but it reads the shared `args.deps`, so a re-grade pushed through `deps` moves its prompt too: it misses the cache, replays, and re-mints its already-consumed `finisher/cleanup-report-1.md`, the identical write-once collision. Its reservation key is `attempts.finish` (`seed('finish')`) — a NEW key this recipe's `attempts.grade`-only bump does not touch. A relaunch that genuinely re-runs finish bumps `attempts.finish` like any lane seed; a relaunch that must not re-run it leaves its prompt bytes alone, which is exactly what `gradeDeps` buys. **The re-grade re-runs because its PROMPT changes** — fresh tag, fresh reserved identity, fresh snapshot path — **not because of the resume alone**: a byte-identical completed call replays cached, and that is exactly how a stale PASS survives a correction (rule 6 + `GRADE_PROMPT`'s empty-tag refusal). A measurement recommending no grade change is recorded and the loop ends there — a relaunch is a decision, not a reflex.

A protocol run reviews twice on the same mechanism at different times, each in its OWN reserved attempt (`references/execution-evidence.md` §1): the script+args as authored, before the writers; and the candidate bytes, before they are ADOPTED. Reviewer ≠ author — the agent that wrote the script never grades its own projection.

The schema field list is unchanged; the hashes are record content, not new schema keys. Hashes establish which bytes were reviewed; they never establish that the projection is faithful, which is the reviewer's own judgement.
   - **Renewed on byte change, and renewal is revalidation — not a human gate.** Any edit to a reviewed input (script, args, plan, contract, or an instruction file the review read) stales THAT review: reconcile the delta, classify it with the existing table (`team-kit-create/references/approval.md` → *Classify changes before asking*), and re-review on the new bytes in a fresh reserved attempt — after retaining the reviewed revision's bytes + SHA-256 under `runtime/scripts/` (`references/execution-evidence.md` §2 *Script revisions*). Identical content reuses the recorded verdict; an editorial change is recorded, reconciled and re-reviewed without a user decision; **only a material commitment the existing authorization does not already cover** goes to the human — and a weakening (an obligation, owner, dependency, seam or grader role dropped or narrowed) is material whatever it is labelled (`references/execution-premises.md` §9). Attaching the old verdict to changed bytes is the stale-PASS vector, not a shortcut.
   - **Scope is this script only.** Saved workflows already on disk are NOT migrated, NOT re-reviewed and NOT invalidated by this promotion (D-PLAN-2 selective-adoption); legacy semantics stand until such a workflow is deliberately re-authored, at which point it is a new authoring and this step applies to it.

5. **RUN** — launch via the `Workflow` tool (resumable; re-pass identical `args` on resume — rule 6).

This rides WITH the platform: Claude authors (native), an optional lint guards, native save persists. Mode-2 = the same minus the committed-save; mode-3 = a previously-saved `/command`. The committed `plan.workflow.js` is a re-authorable build artifact, not load-bearing infra — if the workflow API shifts, re-author against the new surface (do not maintain a brittle generator).

## agentType selection (stage → role)

Pick by capability. Knowledge stages = DEFAULT agent (rule 3); execution stages = custom agentType (rule 2). Don't guess from the roster — use this map. The two projections stay distinct: the default agent's surface comes from the platform, a custom type's comes from ITS frontmatter, and picking a role never silently upgrades it to the default surface.

**A role's `observer:` frontmatter does not arm on this lane.** `team-planner`/`team-designer` declare `observer: intent-keeper` and `team-coder` declares `coder-guard`; those pairings arm on the NATIVE Agent lane only — the workflow lane structurally cannot arm one (`.claude/docs/observer-agents.md:66` HC2: `agent()` has its own resolver with zero references to the arming entry point; workflow-spawned agents got nothing even with a live main-slot observer and the workflow agent's own frontmatter declaring `observer:` — "there is no wire"; `:97` lists the workflow lane first among never-arms). So a workflow dispatch of one of these roles runs UNWATCHED, and **the observer's NAME is never evidence that a guard ran**: silence is the designed steady state either way (`:87`), so citing the frontmatter line — or the guard's absence of complaint — proves nothing about this run. Whatever the observer would have caught is carried here by the explicit review stages, not assumed.

### Codex delegation (opt-in, OFF by default)

A verify stage can run on an OpenAI Codex worker instead of a Claude subagent. **The lane is off unless a plan names it** — there is no config file, no flag and no plan-format field, so a plan that never writes `team-codex-verifier` in a task's `Agent` field cannot reach any of this. Do not assign it on your own judgement; assign it only when the user has asked for it.

**Opting in** is one word — the task's `Agent` field:

```
| **Agent** | team-codex-verifier |     ← instead of team-verifier
```

Everything else is unchanged: same `team-session/` artifact path, same `STATUS:` protocol, same `statusOf` classification.

**Preconditions** — assert these before the stage, not after (a missing one costs a turn to discover):

| Assertion | Expect |
|---|---|
| `command -v codex` | rc 0 — the CLI must be installed |
| `codex login status` | rc 0. Auth rides the **local login**; the lane reads **no API key** and setting `CODEX_API_KEY` does nothing for it |

**Cost** — measured, not estimated: ≈1.4 percentage points of a 30-day free-plan window per turn. A *failed* turn is not a cheap failure: a worker that misreads its instructions does the whole job anyway, and the one measured instance cost more than the passing turn and the smoke turn combined. Front-load the two preconditions rather than retrying.

**Transport failure ≠ gate failure — auto-fallback, don't stop.** The discriminator is the worker's `team-session/{team}/<workerId>.outcome.json`: **the auto-fallback keys on `channel === "transport"`, never on the word `BLOCKED`** — a transport failure (binary unreachable, timeout, unparseable envelope, non-zero exit, a terminal `turn.status` other than `completed`, a schema-invalid or missing final message) is `"channel": "transport"` and does **not** consume reject→re-dispatch retries, and a missing or unreadable `outcome.json` is ambiguous so it counts as transport too — fail closed, never read it as a verdict. This applies to **any** Codex-lane worker, not just `team-codex-verifier`: keying on the word `BLOCKED` was safe only while that one role's preamble left it two legal terminal lines, and generalised it silently swallows the genuine escalation a `team-plan-reviewer` or `team-goal-auditor` exists to raise — `"channel": "semantic"` BLOCKED/NEEDS_CONTEXT is the worker's own judgement and takes the BLOCKED seam row's route (triage-first; human after triage fails). Verdict parity vs the Claude lane was measured identical, so on a transport failure the orchestrator re-runs the SAME stage on the role's Claude twin (`team-codex-verifier` → `team-verifier`) and NOTIFIES — the verdict is recorded in build-state under grader `claude-fallback`, never presented as a Codex verdict. The human re-enters only if cross-vendor independence was the point of the opt-in (then the notify covers it), and any paid/irreversible step gated on this verify still goes through the human checklist regardless of grader. `STATUS: CLEAN`/`errors` mean the worker actually ran and reached a verdict. Treat a **transport** `BLOCKED` as "the seam broke", never as "the gates failed".

**Quality** — verdict parity against the Claude path was measured identical on a seeded 4-failure set (same file, line, column and error text). Delegation changes who runs the gates, not what counts as passing.

## Execution-stage templates (canonical impls: `references/stage-templates.js`)

The 5 canonical shapes in `${CLAUDE_PLUGIN_ROOT}/team-templates/SCHEMA-CATALOG.md` (ResearchFindings / ImplResult / ReviewVerdict / VerifyReport / ACEvidence) describe the on-disk artifact CONTENT each stage writes. Per **rule 9**, heavy stages do NOT force them as a return — they write the artifact to `team-session/` and end BOTH that artifact and their reply with the same `STATUS:` line — the orchestrator parses the RETURNED one (`statusOf`), every later reader reads the WRITTEN one. `schema:` is for LIGHT stages only.

**Close the artifact — and say so in every stage prompt you author.** A stage's verdict is the artifact's OWN last non-empty line, byte-identical to the line the agent returns, nothing after it. The reply is gone by the next resume, fresh `/team-kit-run` boot or evidence selection (§2 selection duty reads the artifact's last non-empty line, not the transcript), so a verdict that lives only in the reply is NOT recorded — and returning the line is not writing it. Canonical statement: `references/execution-evidence.md` §4 terminal status + §10 template — cite it, never re-derive it. Protocol runs get it for free: `bindAttempt`'s `closeTerminal` states it once for both artifact shapes; a stage that does NOT route through `bindAttempt` carries the same sentence in its own prompt. **Carve-out** (a read-only role whose Write is refused cannot satisfy an unconditional form): on any denial the agent follows the write-denial protocol (`team-session-writing`, rule 16) and the same line ends the TEXT it returns for the lead to persist.

**Read `references/stage-templates.js` at author time** (procedure step 3 / entry-mode-1 step 1) and INLINE what you use — workflow scripts cannot import (rule 7). It carries the canonical implementations; every "see the helper below" in the rules table resolves here → to that file:

| In the file | Rule | Purpose |
|---|---|---|
| top-of-script args guard | 6 | fail-loud when `args` dropped on resume — prevents silent full cache-miss + `/repo/undefined*` writes |
| `attemptRef` / `seed` | 6, 7 | derive a stage's RESERVED attempt path from `SESSION` + the orchestrator's epoch/counter (never wall-clock or random — rule 7); refuses traversal, non-segment names, non-positive attempts and path collisions. The frozen ref carries `inputsDir`, the attempt's snapshot slot for consumed MUTABLE bytes: `{root}inputs/` in the directory shape, the sibling `{owner}/{artifact}-{attempt}.inputs/` in the numbered-file shape (reviewers, verifier, goal auditor, runtime preflight) — every producer has one. **Opt-in**: only for a plan declaring the protocol — contract in `references/execution-evidence.md` §1 |

## Output

- Structured result returned to the orchestrator (relay what matters).
- `team-session/{slug}/` artifacts: `prompt.md`, `research/*.md`, plan/review/verify outputs.
- A **human-gated checklist** of prod/irreversible items the workflow did NOT run — plus any blocking SEMANTIC AC marked `NEEDS_HUMAN_EVIDENCE` (a surface no measure pass could reach — `## Measurement`). A run whose only residue is parked evidence ACs exits with the distinct `needs_human_evidence` status — never conflated with failure; on evidence supplied, write the evidence path into the AC row, then relaunch `resumeFromRunId` + identical `args` — the re-grade re-runs because its PROMPT changes (evidence-round tag / the row it reads), not from the resume alone: a byte-identical completed call replays cached.
- **Measurement records** (the reserved `measurer/` attempt records, indexed by the DISPOSITION record) — evidence for the NEXT grade, never this segment's (`## Measurement`). A disposition naming a record that would change a grade takes the SAME relaunch as parked evidence above: path into the AC row, RESERVE the next grade attempt + its `runtime/grade-inputs-{n}.md` selection, relaunch `resumeFromRunId` + identical `args` plus the new `attempts.grade` / `gradeTag` / `gradeDeps` (never the shared `deps`) — **Procedure step 6**, which owns the recipe. Unrelaunched, the lane is write-only.
- `<session>build-state.md` — the AC ledger (every blocking AC → pending/passed/failed/needs-human + grader + verdict; ids carry human slugs, e.g. `AC-3 gates-green`) + loop counters + `PD-n` rulings. The run is DONE only when every blocking AC reads `passed` and mechanical gates are green.

## Reproducibility tiers

Most → least canned: saved `/command` workflow  >  authored + linted + saved `plan.workflow.js` (mode-1)  >  ad-hoc orchestrator-authored (mode-2). For recurring shapes, save the script as a `/command` (`.claude/workflows/`, with `meta.whenToUse`); for bespoke reproducible work, mode-1 (author → lint → save); for one-offs, mode-2 — which still leaves an editable persisted script (every invocation persists under the session dir): iterate via edit-file + `{scriptPath}` + `resumeFromRunId`, the documented loop that narrows the mode-2/mode-1 gap.
